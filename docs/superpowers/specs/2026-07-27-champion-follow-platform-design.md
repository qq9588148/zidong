# 胜率冠军跟单平台设计

日期：2026-07-27

状态：对话设计已获用户批准，等待书面规格复核

目标平台：Windows 执行端优先；macOS 后续复用；手机仅只读

首版游戏：同一平台、同一房间、同一期号和赔率的比特分分彩

## 1. 目标

建立一套中央协调平台，持续采集公开的玩家下注与开奖结果，按匿名用户建立长期胜率画像，从中产生“胜率冠军”跟单信号，并把不同合格信号分配给已授权的 Windows 客户端。

首版必须做到：

1. 主采集机持续运行时，用户画像和冠军榜持续累积，不依赖普通用户打开 App；
2. 普通用户使用一次性授权码注册，一个账号只绑定一台设备；
3. Windows App 使用内置浏览器，用户手动登录平台并由本机保管会话；
4. 每台设备每期最多下注一个“球位＋方向”；
5. 只使用胜率冠军体系，不使用庄家盈利方向、庄家心理或庄家操盘信号；
6. 下注频率由冠军信号门槛自然控制，不按日强制补足下注次数；
7. 多设备尽量使用不同合格信号，避免长期形成完全相同的下注序列；
8. 平台订单结算是盈亏主依据，账户余额变化只用于复核；
9. 管理员可查看每个用户的余额、分周期输赢、设备、信号和订单；
10. 所有决定、订单、结算和策略修改均可审计且不泄漏凭据或真实第三方玩家标识。

本系统只能验证“历史冠军信号在之后的逐期盲跟表现”，不能承诺过去运气会延续，也不能承诺盈利或避免连续亏损。

## 2. 明确不做的内容

首版不做：

- 庄家方向、庄家压力、庄家操盘或玩家总金额反推开奖；
- 无冠军信号时随机下注、反向下注或用其他策略补单；
- 强制达到每日固定下注比例或固定下注次数；
- 控制任意外部浏览器；
- 手机端采集、计算或下注；
- 采集或展示第三方玩家的真实 UID、昵称、密码、Cookie、Token 或余额；
- 数字、龙虎、和等首版范围外玩法；
- 先完成一套独立 Mac 执行端再移植到 Windows。

## 3. 已确认的首版玩法

每个球仅支持以下双面方向，赔率均为 1.96 倍（含本金）：

- 大 / 小；
- 单 / 双；
- 质 / 合。

五个球共 30 个可执行单项：

```text
P1:大 ... P1:合
P2:大 ... P2:合
...
P5:大 ... P5:合
```

每台设备每期最多执行其中一项。若平台赔率、玩法编码或结算合同变化，执行端必须失败关闭，等待规则版本更新，不能继续按旧合同下注。

平台不允许同一用户在同一玩法同时保留相反方向。系统必须先应用能够明确归属的撤单，得到当前有效净下注；只有净下注仍同时存在相反方向时才标记采集异常，不把“先下注、撤单、再改投相反方向”误判为对压。

## 4. 总体架构

### 4.1 组件

系统由五个组件组成：

1. **主采集端**
   - 使用受控的内置 Chromium 长期登录同一游戏房间；
   - 使用不与普通执行客户端复用的平台会话，避免同账号登录互相踢出；
   - 采集公开下注回执、撤单提示、期号、封盘状态和开奖结果；
   - 在页面隔离环境中把第三方玩家标识转换为稳定匿名键；
   - 先把标准化且脱敏的事件写入本机持久队列，再可靠上传服务器。

2. **中央服务端**
   - 保存权威事件、用户画像、冠军榜、信号、设备任务和结算；
   - 增量更新画像，不在每次客户端上线时重新扫描全量历史；
   - 为每台在线设备生成版本化任务；
   - 通过 TLS WebSocket 向客户端实时下发最新任务。

3. **Windows 客户端**
   - 注册、登录并绑定设备；
   - 在 App 内置 Chromium 中由用户手动登录平台；
   - 验证本期期号、倒计时和页面合同；
   - 在安全提交时点执行服务器最新任务；
   - 回传平台订单确认、结算、余额和性能数据。

4. **管理员后台**
   - 管理授权码、账号、设备、信号门槛和全局停止开关；
   - 查看用户余额、输赢、订单、画像、信号、异常和延迟；
   - 记录全部管理操作审计。

5. **手机只读页面**
   - 后期复用管理员或用户后台的响应式网页；
   - 只查看状态、信号、订单、余额和输赢；
   - 不执行平台登录和下注。

### 4.2 技术方向

- Windows 与 macOS 客户端采用 Electron，并固定同一版本的内置 Chromium；
- Windows 是首个实现和验收平台；
- macOS 后续复用同一客户端代码，不把 Mac 验收当作 Windows 验收；
- 中央业务核心沿用 Python 领域逻辑，服务接口采用异步 HTTP/WebSocket；
- 权威持久化采用 PostgreSQL；
- 首版不为了 100 台规模引入不必要的微服务或消息队列，单服务进程加数据库即可；
- 高频当前期状态可保存在服务进程内存中，所有权威事件和状态转换必须事务落库。

主采集端的本机持久队列采用追加写入和单调序号：服务器只确认已经事务落库的最高连续序号；主采集端只清理已经确认的数据。网络或服务器短暂中断后按序幂等重放。若本机写入失败且上游事件无法重新获取，受影响期必须标记为不完整，不能继续产生画像或信号。本机队列同样只能保存脱敏事件。

### 4.3 连接边界

- 主采集端和普通客户端均主动连接服务器，家庭网络无需开放入站端口；
- 平台密码、Cookie、Token 和完整请求对象永不上传服务器；
- 服务器不代替用户登录彩票平台；
- 主采集端掉线不影响既有历史画像，但立即停止产生新的可执行冠军信号；
- 普通客户端掉线时停止下注，不使用离线策略。

## 5. 匿名用户身份与历史迁移

### 5.1 匿名身份

页面桥接器可以读取公开下注回执里的玩家候选标识，但必须在页面隔离环境中立即生成 HMAC 匿名键：

```text
actor_key = HMAC-SHA256(identity_namespace_key, platform_actor_id)
```

要求：

- 原始标识不得离开页面桥接器；
- 匿名键在主采集端重启后保持稳定；
- 身份命名空间密钥只由权威主采集端使用，并由系统安全存储保护；
- 日志、API、测试输出和后台均不得显示原始标识或命名空间密钥；
- 后续增加备用采集端时，必须受控加入同一匿名命名空间，否则不能合并画像。

身份命名空间具有不可变版本号。启用真实画像前，密钥必须完成加密备份和恢复演练；备份由服务器密钥管理或独立恢复密钥保护，不以明文写入 PostgreSQL、日志或代码。正常运行不轮换该密钥。若因泄漏必须更换，则建立新的命名空间；只有在过渡期重新看到同一原始平台标识时才能建立受审计的旧新匿名键别名，不能猜测合并未再次出现的历史用户。

“不同匿名键”只表示不同的平台候选标识，不证明背后一定是不同自然人。

### 5.2 当前数据

现有日志已经保存匿名用户、期号、玩法、金额和时间。只有在安全沿用现有身份命名空间密钥并验证解析版本兼容时，才可作为当前画像初始数据；否则只能作为总体历史基线，不能延续到新匿名用户画像。现状不包含第三方玩家余额，也不需要余额来计算胜率。

迁移时必须：

1. 只从权威、完整的 `source_events` 导入；
2. 验证匿名命名空间与新主采集端一致；
3. 不能确认命名空间一致的数据放入独立历史分区，不与当前匿名用户强行合并；
4. 导入过程去重并保留来源、版本和校验摘要；
5. 现有 Mac 主机可在 Windows 版本开发期间继续采集，迁移后从最后事件位置增量续接。

## 6. 采集完整性与撤单

### 6.1 权威事件

每个标准化事件至少包含：

- 脱敏事件键；
- 匿名玩家键；
- 平台事件时间和本机接收时间；
- 期号；
- 球位和方向；
- 金额；
- 事件种类；
- 数据来源和解析版本。

同一用户、同一期、同一方向的多次追加保留原始事件，但画像结算时合并为一个预测。下注金额不参与用户排名。

### 6.2 缺口与重复

- 事件键必须幂等去重；
- 历史回填与实时事件重叠不得重复计数；
- 采集断档、解密失败、期号不确定或结果不完整时，该期不得进入画像或信号；
- 主采集端必须持续发送包含当前期号和页面状态的心跳；心跳超过 1 秒未更新时，服务端将当前信号标为不可执行，不能把“本期暂时没人下注”误判为采集端离线；
- 恢复后从已确认锚点补齐，不能把缺口两端直接拼接为完整期。

### 6.3 无法归属的撤单

当前部分分分彩撤单提示不能可靠关联到匿名用户、玩法和金额。能够明确归属的撤单先从该用户当前有效下注中扣除；无法归属时采用保守规则：

- 出现无法归属的撤单时，该期总流水日志仍保存；
- 整期不计入任何匿名用户的胜率画像；
- 整期不产生冠军跟单信号；
- 不允许根据金额、时间或顺序猜测撤单归属；
- 后续若被动确认到权威关联字段，再以新解析版本恢复精确统计。

## 7. 用户画像

### 7.1 统计单元

冠军信号按 15 个市场分别建榜：

```text
5 个球位 ×（大小、单双、质合）
```

一个统计样本是：

```text
(匿名用户, 期号, 球位, 玩法对)
```

同一用户在该样本内的追加只算一次方向预测。不同球位或不同玩法对分别计样本。总体榜作为辅助展示，实际信号优先使用对应市场的分类画像。

### 7.2 胜负与单位回报

只按固定 1 元结算，不按玩家实际下注金额加权：

- 命中：净收益 `+0.96`；
- 未命中：净收益 `-1`；
- 和局：首版双面玩法不存在；若平台规则变化产生回本，则记 0 且不进入二元胜率分母。

```text
原始胜率 = 赢 / (赢 + 输)
固定单位回报率 = (0.96 × 赢 - 输) / (赢 + 输)
盈亏平衡胜率 = 1 / 1.96 = 51.020408...%
```

### 7.3 保守胜率

不能用粗胜率直接排名。初始统计版本采用一侧 95% Wilson 下界：

```text
p_lower = WilsonLowerBound(赢, 赢 + 输, z = 1.6448536269514722)
```

为避免近期已经失效的长期冠军继续占榜：

- `p_all` 是全部有效样本的一侧 95% Wilson 下界；
- 样本达到 50 后，`p_recent` 是最近最多 200 个有效样本的一侧 95% Wilson 下界；
- 保守胜率取 `min(p_all, p_recent)`；
- 少于 50 个样本时只使用 `p_all`。

```text
保守单位回报率 = 1.96 × 保守胜率 - 1
```

统计公式和参数必须带版本。后续调整只能影响之后产生的信号，历史订单继续保留当时使用的版本。

### 7.4 逐期盲跟验证

每期开奖前保存当时仅由过去数据得到的排行榜和候选信号；开奖后按固定 1 元结算。不得用完整历史先挑出冠军，再假装从历史第一期开始跟随。

画像至少记录：

- 有效样本、赢、输和原始胜率；
- 全量及近期保守胜率；
- 固定单位回报率和保守单位回报率；
- 逐期盲跟次数、收益和最大回撤；
- 首次和最后出现时间；
- 可跟单次数、来不及跟单次数和可跟单率；
- 分类排名、总体排名和版本。

“可跟单”按设备实际安全提前量计算：一条公开下注从主采集端到达时，距离该期封盘仍不少于该设备当时的安全提前量，才计为可跟单。后台显示的是设备相关的可跟单率，不能用固定秒数替代不同设备的真实延迟。

### 7.5 用户分级

- 少于 30 个有效预测：观察用户，不产生任务；
- 30～199 个：候选用户，单期最多只能分配给一台设备；
- 至少 200 个、至少 50 个已结算逐期盲跟信号且逐期盲跟固定单位回报率大于 0：正式高手池；
- 至少 500 个、至少 200 个已结算逐期盲跟信号且逐期盲跟固定单位回报率大于 0：核心高手池；
- 用户级别是全局画像属性，只由本节的样本量、已结算逐期盲跟数和逐期盲跟回报条件决定，并带独立版本；不受任一设备门槛影响。级别条件不再满足时自动降级，设备门槛只决定该设备是否执行该用户的当前信号。

## 8. 冠军信号门槛与频率

### 8.1 门槛

管理员可配置全局默认值，并可对单台设备覆盖：

- 最低用户级别；
- 最低保守胜率；
- 最低保守单位回报率；
- 最低可跟单率。

固定 1.96 赔率下，“最低保守胜率”和“最低保守单位回报率”是同一条件的两种显示。执行时统一换算为：

```text
有效最低保守胜率 = max(
  配置的最低保守胜率,
  (配置的最低保守单位回报率 + 1) / 1.96
)
```

二者不作为两份独立证据重复加权。

信号还必须满足：

- 当前下注来自已完成画像的匿名用户；
- 当前球位和方向属于首版玩法；
- 当前期完整且不存在无法归属的撤单；
- 当前用户在该市场的逐期盲跟规则满足配置；
- 信号出现时间仍早于该设备的安全提交截止。

### 8.2 频率口径

系统不设置“每天必须下注 X%”的配额，也不为了补频率降低数据真实性。

下注频率通过门槛自然控制：

- 门槛提高，信号更少；
- 门槛降低，信号更多；
- 没有合格信号时允许连续跳过；
- 不再使用“至少参与 50%”或“最多连续跳过 3 期”的硬约束。

后台必须展示当前门槛在最近 7 天和 30 天的：

- 可执行信号数和信号频率；
- 原始胜率、保守胜率；
- 固定 1 元逐期盲跟收益；
- 实际设备订单收益。

门槛预览只能过滤每一期开奖前已经冻结的 `as-of` 画像、榜单和候选信号快照，再用之后开奖结果结算。禁止拿今天的冠军榜或今天计算出的用户画像回套过去 7 天、30 天，否则属于未来信息泄漏。

修改门槛只影响未来信号，不允许自动搜索并应用历史回报最高的门槛。

首次安装没有隐含的可执行门槛。管理员必须查看 7 天和 30 天估算结果并显式保存一份版本化门槛配置后，系统才允许产生真实任务。

## 9. 当前期多方向处理

冠军用户同一期可以购买不同球位或不同玩法。处理规则：

- 每个“球位＋方向”形成独立候选信号；
- 同一方向的追加合并为一次预测；
- 不按本期金额大小决定优先级；
- 优先级由该用户对应分类的保守单位回报率决定；
- 一台设备每期仍最多执行一个候选；
- 多台设备可分别跟随同一冠军本期不同的合格方向。

排序相同时依次使用：更高可跟单率、更多有效样本、稳定匿名键顺序。该顺序必须确定且可回放。

## 10. 多设备分配

### 10.1 少量设备

前期 1～3 台设备按以下规则：

- 每一期按版本化服务器分配种子、期号和设备公钥摘要计算确定性轮换顺序；
- 轮换顺序中的第一台获取排名最高的合格信号，后续设备依次获取下一个不同的合格信号；
- 轮换必须令长期获得第一优先级的次数尽量均衡，不能让固定“设备 1”长期独占最高信号；
- 普通信号同一“球位＋方向”最多分配 1 台；
- 两个不同匿名冠军同时给出相同方向、二者均至少属于正式高手池且分别满足对应设备门槛时，最多分配 2 台；
- 没有其他合格冠军信号的设备跳过。

“两个不同匿名冠军”不是对两个自然人身份独立性的证明。

每次分配必须保存在线且已开启的设备集合、种子版本、候选信号版本和最终结果。设备上下线引起的重新分配只能产生更高任务 revision；已经进入平台提交的设备不得被重新分配第二项。

### 10.2 扩展设备

| 在线设备数 | 同一精确方向正常上限 | 双冠军强信号上限 |
|---|---:|---:|
| 1～3 | 1 台 | 2 台 |
| 4～9 | 2 台 | 3 台 |
| 10 及以上 | 在线且已开启设备的 20% | 在线且已开启设备的 35% |

当在线且已开启自动下注的设备数为 `N >= 10` 时，正常上限取 `max(1, floor(N × 20%))`，双冠军确认上限取 `max(正常上限, floor(N × 35%))`，不得用四舍五入突破比例上限。

分配器还必须满足：

- 任意两台设备连续执行完全相同的已下注方向不得超过 3 次；双方共同跳过的期数不重置也不增加该连续计数；
- 达到限制时选择下一个合格冠军信号，否则跳过；
- 不允许为了分散而故意反买冠军；
- 不允许退回庄家算法或随机方向；
- 每个任务包含期号、设备、单调 revision、动作、信号版本、匿名冠军、球位、方向、门槛摘要、到期状态和服务器签名；客户端必须验证签名、设备、期号、revision 和有效期。

任务动作只有 `BET` 和 `CANCEL`。对同一“设备＋期号”，客户端只接受最高 revision：冠军撤单、画像降级、门槛不再满足、采集心跳过期、数据缺口或重新分配都必须发布更高 revision 的已签名 `CANCEL` 墓碑。乱序到达的旧 `BET` 永远不能恢复为可执行状态；断线重连后必须先读取服务端当前最高 revision。

## 11. 跟单时机

采用“临近封盘按冠军最新净下注跟单”，不在冠军首次下注后立即执行。

流程：

1. 冠军下注产生临时候选；
2. 追加、可识别撤单和榜单变化更新候选版本；
3. 服务端持续向客户端推送该设备的最新 revision；任何失效都推送 `CANCEL`，不能只在服务端静默删除信号；
4. 客户端依据本地平台倒计时和最近真实提交延迟计算安全提交时点；
5. 到达安全时点时冻结最新完整任务并提交；
6. 任务在提交前变化且仍有时间时只使用最高 revision；最高 revision 为 `CANCEL` 时不提交；
7. 已经进入不可可靠成交区间的新信号直接跳过并记录 `late_signal`；
8. 平台确认订单后不得因后续信号变化再次发送。

安全提前量不是固定常数：

```text
安全提前量 = 最近提交链路 P99 + 安全余量
```

初期预计在封盘前约 1.5～2 秒执行，但只有 Windows 实机数据可以决定最终值。期号和倒计时以客户端当前页面为最终校验，不能只相信服务器墙钟。

## 12. 金额与追本

### 12.1 每设备独立金额链

每台设备独立维护：

- 起始下注金额；
- 单注上限；
- 当前未追回亏损；
- 当前追本轮次；
- 最近已确认订单和结算。

金额链属于设备，不属于冠军用户：

- 跳过期不清零；
- 从冠军 A 切换到冠军 B 不清零；
- 赢、触发上限重置或管理员明确开始新一轮时清零。

### 12.2 只追回本金

首注使用用户配置的起始金额。输后只要求追回累计未追回亏损，不额外要求一份目标利润：

```text
下一注 = 向上取整到平台下注单位(累计未追回亏损 / 0.96)
```

例如起始 10 元输掉后：

```text
ceil(10 / 0.96) = 11 元
```

11 元中奖净收益 10.56 元，清除 10 元未追回亏损；多出的 0.56 元只是整数取整结果，不是固定利润目标。

若 11 元再次输掉，未追回亏损为 21 元：

```text
ceil(21 / 0.96) = 22 元
```

### 12.3 上限与异常

- 所需金额超过单注上限时，关闭当前追本轮次，把未追回金额保留为已实现历史亏损，并从下一次合格信号恢复起始金额；
- 余额不足时停止，不缩小金额假装完成追本；
- 上一注结算未知时冻结金额链；
- 平台赔率、限额或最小下注单位变化时失败关闭；
- 修改起始金额表示用户明确开始新一轮，旧轮次不再追本，但历史盈亏不得抹除；
- 金额使用整数最小单位计算，禁止二进制浮点误差。

## 13. 账号、授权与设备绑定

### 13.1 普通用户

- 管理员后台生成一次性授权码；
- 用户注册必须输入有效授权码；
- 授权码使用后立即作废；
- 一个 App 账号绑定一台设备；
- 设备首次注册生成不可导出的设备密钥，服务端绑定其公钥；
- 换电脑或重装后必须由管理员手动解绑；
- 用户端可设置起始金额和单注上限；信号门槛的全局默认及单设备覆盖均只能由管理员设置，用户端只读显示当前生效门槛；
- 用户端不能修改算法公式、排名规则或全局策略版本。

### 13.2 管理员

首版只有一个超级管理员账号：

- 必须启用双重验证；
- 可生成授权码、解绑设备、停用账号；
- 可修改全局及单设备门槛；
- 可停止全部自动下注；
- 所有操作记录操作者、时间、旧值、新值和原因；
- 首版不实现客服、财务或员工多角色权限。

App 密码只保存强密码哈希；一次性授权码在数据库中也只保存不可逆摘要。设备、管理员和服务端会话必须有独立撤销能力，撤销后旧会话和未执行任务立即失效。

Windows 客户端不得保存 App 明文密码。App 刷新令牌保存在 Windows Credential Manager，设备私钥使用 Windows CNG/DPAPI 保护；平台 Session 保存在独立 Chromium Profile，并使用 Windows OS 加密能力保护。退出平台账号、管理员解绑设备或用户清除本机会话时，必须分别删除对应的 Credential Manager 项、设备会话和 Chromium 平台存储。macOS 后续使用 Keychain 提供等价边界。

## 14. Windows 客户端

### 14.1 浏览器隔离

- 平台网页运行在独立 Electron Session；
- 禁用网页 Node.js 权限并启用上下文隔离和沙箱；
- 页面只能通过最小白名单桥接器向主进程发送标准化事件；
- 不控制 Chrome、Edge、Multilogin 等外部浏览器；
- 用户首次手动登录平台，之后复用本机加密会话；
- 登录失效时停止下注并提示用户重新登录。

### 14.2 主界面

主界面必须直接显示：

- 服务器、主采集机和平台连接状态；
- 当前期号和倒计时；
- 本期有无冠军信号；
- 当前跟随的匿名冠军、球位和方向；
- 该信号的用户级别、有效样本量、保守胜率、保守单位回报率和可跟单率；不得再生成一个未定义的黑盒“信号质量分”；
- 计划下注金额和预计提交时间；
- 上一注跟随对象、方向、金额、输赢及金额调整原因；
- 当前平台余额、本轮输赢、今日输赢和累计输赢；
- 当前未追回亏损、起始金额和单注上限；
- App 内开启/停止自动下注按钮。

自动下注默认关闭。只有用户在 App 内明确开启后才能发送订单。

### 14.3 断线与恢复

- 设备断网、平台掉线、主采集数据过期、期号不一致或结算未知时停止；
- 恢复后先同步期号、最近订单、结算和金额链；
- 不补发过期订单；
- 不跨浏览器 Session 或 App generation 重发旧订单；
- 同一期、同设备、同轮次最多一个平台确认订单。

## 15. 盈亏与余额

### 15.1 权威顺序

1. 平台已确认并结算的本账号订单；
2. 本账号平台余额快照用于复核；
3. 两者不一致时标记“未识别余额调整”，不擅自改写订单盈亏。

充值、提现、赠送、返点和人工调账不计入下注输赢。未能取得平台资金流水时，余额差额只作为未识别调整展示。

客户端只能从已经被动确认的页面字段或平台响应读取本账号余额；无法确认余额来源时显示“余额不可用”，不得根据订单反推一个伪余额。

### 15.2 时间周期

所有报表按 Asia/Shanghai 自然时间计算：

- 日：00:00 至次日 00:00；
- 周：周一 00:00 至下周一 00:00；
- 月、季度、年度按自然日历；
- 累计从账号首个已结算订单开始。

## 16. 管理员后台

### 16.1 总览

- 主采集机状态、数据延迟和当前期号；

## 17. 数据模型与留存

中央数据库至少需要以下边界清晰的实体：

- App 账号、设备和授权码；
- 采集端实例和健康状态；
- 游戏期次和开奖结果；
- 匿名玩家事件；
- 玩家分类画像和榜单快照；
- 冠军信号及其版本；
- 设备任务；
- 执行订单和平台确认；
- 结算和余额快照；
- 金额轮次；
- 策略配置版本；
- 管理与安全审计。

留存规则：

- 下注、开奖结果、画像、信号、任务、订单、结算和审计长期保存；
- 高频相同快照只保留状态变化和必要性能摘要；
- 脱敏诊断日志保留 30 天；
- 不保存真实第三方 UID、平台密码、Cookie、Token 或完整私有请求；
- 数据库每日备份，并定期执行实际恢复验证。

## 18. 正确性与性能不变量

必须始终成立：

- 每台设备每期最多一个平台确认订单；
- 旧期号、旧任务版本、旧会话和重复请求不得发送；
- 对同一设备和期号，低 revision 的 `BET` 不能覆盖高 revision 的 `CANCEL`；
- 只执行服务器产生的冠军信号；
- 没有冠军信号时不调用任何替代下注算法；
- 金额严格按已确认结算推进；
- 主采集数据过期、撤单不明或采集不完整时不下注；
- 原始身份和网页登录凭据不进入服务器或日志。

系统分别记录：

- 网页消息到主采集端；
- 主采集端到服务器；
- 画像更新与设备分配；
- 任务到客户端；
- 客户端提交到平台确认。

每段输出 P50、P95 和 P99。安全提交提前量只由 Windows 实机链路数据校准，不能用 Mac 数据代替。

## 19. 测试

### 19.1 画像与信号

- 固定金额标准化结算；
- 盈亏平衡胜率；
- Wilson 下界边界和统计版本；
- 全量与近期样本；
- 30/200/500 分级边界；
- 同期追加只算一次；
- 多球、多玩法独立信号；
- 已识别撤单后改投相反方向的净下注；
- 缺口、重复、错误期号和无法归属撤单排除；
- 每期只使用之前数据的逐期盲跟回放；
- 7 天、30 天门槛预览只过滤历史 `as-of` 快照；
- 门槛变化不改写历史任务；
- 用户全局级别与单设备执行门槛相互独立。

### 19.2 分配与金额

- 1～3、4～9、10 台以上的分配上限；
- 设备上下线和重启后的确定性轮换、分配重放及长期第一优先级均衡；
- 任意两设备不连续超过 3 次执行同序列；
- 无其他合格信号时跳过；
- 切换冠军和跳过不清除金额链；
- `ceil(loss / 0.96)` 的整数边界；
- 赢、连输、单注上限、余额不足和未知结算；
- 修改起始金额开始新轮但不抹除历史盈亏。

### 19.3 执行与故障

- 一期一单和幂等任务；
- `BET`、`CANCEL` 墓碑、乱序和断线重连只接受最高 revision；
- 最晚安全时点和 `late_signal`；
- 平台拒绝、超时、未知订单和历史订单恢复；
- 客户端、采集端、服务器和数据库分别重启；
- 主采集本机持久队列、服务端 ACK 游标、离线积压和幂等重放；
- 匿名命名空间密钥加密备份、恢复和版本不变性；
- 网络分区、时钟漂移和平台 Session 失效；
- 100 台客户端并发连接、任务分配和结算回传；
- 数据库备份恢复和报表周期边界；
- Windows Credential Manager、CNG/DPAPI、平台 Session 清除和会话撤销；
- API、日志和测试夹具的隐私字段扫描。

## 21. 首版成功标准

首版只有同时满足以下条件才算完成：

8. 管理员能查看每个用户的当前余额及日、周、月、季度、年度、累计输赢；
9. 100 台合成并发测试无重复下注、串号或跨设备状态污染；
10. 凭据、原始第三方身份和私有请求不出现在 API、日志、数据库明文或测试产物中。
